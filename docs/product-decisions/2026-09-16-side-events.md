# Detour 小插曲系統決策紀錄

日期：2026-09-16
狀態：已定案，後續產品／程式實作應以本文件為準；與舊版 `PRODUCT_FOUNDATION.md` 或現有 mission model 衝突時，以本紀錄作為最新決策。

## 1. 定位

- 消費者介面不把這套內容視為「任務」。
- 它們是旅途中穿插的「小插曲」／注意力目標，用來讓使用者在繞路時持續注意周遭，而不是增加待辦壓力。
- 不設完成條件、不要求使用者確認完成、不建立成功／失敗概念。
- App 不需要知道使用者是否真的找到或做了該項內容。

## 2. 內容原則

- 小插曲必須客觀：看得到、做得到、可直接判斷，不要求情緒詮釋或主觀評分。
- 不做會干涉導航的「選擇型」內容，例如叫使用者在路口自行選方向。
- 不要求折返，也不應把使用者帶離 Detour 的導航主線。
- 需要特定環境條件的小插曲，只能根據尚未走過的前方路線／Scene 條件安排。
- 任何時候只顯示 1 個 active 小插曲，避免形成多項待辦清單。

## 3. 更換機制

- active 小插曲旁提供「沒感覺，換一個」。
- 更換次數不設上限。
- 使用者主動更換不算失敗、不記錄為未完成，也不消耗該旅程原本規劃的小插曲時段數。
- 同一時段內可連續更換多次；下一個正式時段仍由旅程進度觸發。

## 4. 可選旅程時間

正式 UI 改為：

- 10 / 15 / 20 / 25 / 30 / 35 / 40 / 45 / 50 / 55 / 60 分鐘
- 最低 10 分鐘
- 最高 60 分鐘
- 每 5 分鐘一個可選區段

這取代舊版 15 / 30 / 45 / 60 / 90 分鐘設定。

## 5. 每趟小插曲數量

- 10–15 分鐘：3 個
- 20–25 分鐘：5 個
- 30–35 分鐘：7 個
- 40–45 分鐘：9 個
- 50–60 分鐘：10 個

設計密度約為平均每 4–5 分鐘出現一次新的小插曲，但「5 分鐘」只是密度目標，不是固定計時器。

## 6. 觸發原則

小插曲採「進度驅動，時間兜底」，不使用固定每 5 分鐘跳一次的機械排程。

判斷優先順序：

1. 路線進度：依使用者已走完的 route 比例／未走路段推進情況安排下一個小插曲。
2. 有效移動時間：長時間幾乎無位移（例如等紅燈）時，不應因牆上時間經過就直接洗掉目前內容。
3. 導航情境：複雜路口、過馬路、即將轉彎等需要注意導航／安全的時刻，不同時推送新的小插曲。
4. 時間上限兜底：若使用者長時間停留在同一個小插曲，仍要在合理上限後自然換新，避免整段旅程只掛著同一項。

更適合把每個預定觸發點視為一個 trigger window，而不是精確時間點；系統在合理進度範圍內找自然、安全的時機切換。

## 7. 系統模型方向

舊版 `Mission -> completion -> completed/skipped` 模型應逐步淘汰。

新版概念應更接近：

- 一個 active side event
- 一組旅程時段／trigger windows
- 使用者可無限 replacement
- 不追蹤完成狀態
- route / scene context 決定哪些內容適合出現
